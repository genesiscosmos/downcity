# Accounts login and delivery protocol

All endpoints below are under `/v1/accounts`. Fields use snake_case. Login secrets and tokens must never appear in URLs, analytics or logs. All successful login JSON responses use `Cache-Control: no-store`.

| Endpoint | Request JSON | Response |
| --- | --- | --- |
| POST login/start | `provider`, `bureau_id`, required `client_type`; OAuth additionally `redirect_uri`, `state`, `code_challenge`, `code_challenge_method: "S256"` | `login_id`, private `login_secret`, `provider`, `status`; OAuth additionally `url`; Email additionally `inputs` |
| POST login/continue | `login_id`, `login_secret`, `input: {email,password}` | `done` without token; only Email accepts input |
| POST login/result | `login_id`, `login_secret` | `pending` or `done`, `login_id`, `provider`; never a token |
| POST login/exchange | `login_id`, `login_secret`, `exchange_id`; all OAuth also `authorization_code`, `code_verifier` | `done`, `login_id`, `provider`, `user_token` |
| POST logout | Current User Token in Bearer authorization | `{success:true}` after `ctx.revoke_user_token` completes |
| POST verify-email | `token` | `{success:true,message}`; never a User Token |

`client_type` must explicitly be `web`, `cli`, or `desktop`. Every OAuth transaction supplies a callback, an independent random product state, and S256 PKCE. The authorization URL contains only the public login ID; it binds the Provider browser with a host-only HttpOnly SameSite=Lax cookie before redirecting with an independent Provider OAuth state. HTTPS uses Secure and `__Host-`; HTTP is limited to local development. Provider callback consumes that state once and requires the bound browser.

Website `redirect_uri` must exactly match the registry's Bureau `server.server_url` with `/api/auth/callback` appended. HTTPS is required except for loopback development. Arbitrary caller-selected HTTPS targets are rejected. A BFF initiates login through a same-origin POST, stores state, verifier, login proof, and exchange ID in a short-lived host-only HttpOnly cookie, validates the returning browser transaction and state, then exchanges the callback authorization code to create a website session. Production and local development websites use separately registered Bureau URLs. Direct same-origin web clients retain the same product callback and PKCE requirements. Email/local web login additionally requires same-origin Origin and the initiating Federation browser cookie.

CLI/Desktop use a canonical `http://127.0.0.1:<unprivileged-port>/<callback-path>` without credentials, query, or fragment. `@downcity/federation/node` exposes `create_loopback_login_callback`, which owns a random local port, random callback path, state, verifier, and timeout. Only a single GET with the exact Host/path, unique code/state parameters, and matching state is accepted. The host releases it on cancellation, expiry, window close, or quit. CLI requires a local system browser; remote/headless OAuth is unsupported.

After provider authentication, all products automatically receive a redirect carrying a single-use `code` and their original callback `state`. The product validates its callback binding and exchanges `authorization_code`, `code_verifier`, and `login_secret`. No Token is signed until all proofs pass, and status remains pending until exchange. Provider authorization remains in place. Callback redirects use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

Flows expire after five minutes. An atomic conditional database update accepts exactly one exchange ID. Use a random URL-safe 20–128-character identifier (UUID works), generated before the first exchange request and reused after transport failures. Identical exchanges recover the same token for 60 seconds after the first accepted exchange; a different exchange ID receives 409. After expiry, restart login. A request whose response was lost must not create a new exchange ID. State queries remain separate from exchange.

`FederationAccount.login()` supports input and host-managed OAuth. Its `on_authorize(url)` returns `{ authorization_code, code_verifier }` only after the host validates its callback. Cross-page web BFFs use `login_start()` and `exchange()` separately. `status(login_id, login_secret)` restores securely retained initiating proof but never authorizes OAuth delivery. SDK retains the same exchange ID across failed network calls; repeat `exchange({ authorization_code, code_verifier, exchange_id })` with the original proof and ID. `await logout()` revokes remotely before clearing local credentials; failure retains credentials for retry.

Email/password authentication is disabled in better-auth when the Email provider is unavailable. When enabled, verification is mandatory, signup sends verification mail, and verification does not auto-sign in. A successful password response must contain a nonempty user ID, email and explicit `emailVerified: true` before signing a token. `/auth/*` only permits GET `/auth/verify-email` when Email is enabled; callback redirect parameters are ignored and other native sign-in/linking/session endpoints are closed. The dependency API is called with `verifyEmail({query:{token},asResponse:true})`, and both HTTP success and `status:true` are checked.

OAuth identities resolve by provider plus provider user ID. Emails, including unverified or synthesized emails, never cause automatic linking. A collision blocks login with an account-linking/recovery hint. Existing primary email and verification status are not overwritten by a provider profile. New user plus provider identity insertion is atomic, and initialization installs a unique provider identity index. Existing duplicate provider identities prevent initialization and require explicit operator review; no account/history is deleted or merged.

SQLite and PostgreSQL preparation create the registered `service_accounts_login_flows_v4` table, discard obsolete temporary login transactions, and check the provider identity index. Accounts and historical sessions are preserved. Provider callback rotates OAuth state; exchange retains its token response only for the bounded retry window. Expired rows are inaccessible immediately and are physically removed during startup and subsequent login operations; there is no independent idle database cleanup scheduler in this module.
