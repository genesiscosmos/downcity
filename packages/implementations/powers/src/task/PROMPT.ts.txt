# Task Power

Task represents a piece of work. Inbox, Todo and Calendar are different entry points into the same tasks. Agent execution and scheduling are optional capabilities.

## Identity and storage

- Each task has a stable `task_id`, independent of its editable title. Duplicate titles create separate tasks.
- Definitions live in the TaskPower City store at `tasks/<task_id>/task.md`; runs live beside the definition.
- `list` and `create` return task IDs. For existing actions whose selector is named `title`, pass the stable task ID. A unique title can also locate a task; ambiguous titles fail explicitly.
- Work status (`pending`, `in_progress`, `review`, `completed`, `cancelled`), schedule status (`enabled`, `paused`, `disabled`) and Run status are different.

## Kinds and timing

- `kind=self`: personal todo or reminder. A title is sufficient; no execution Agent or Workspace is needed. Do not call `run` for personal todos.
- `kind=agent`: reusable execution instructions. Describe the goal, input, scope, constraints, completion criteria and exact final deliverable.
- `kind=script`: a non-empty executable script body.
- `when=@manual`: no automatic trigger.
- `when=time:<ISO8601-with-timezone>`: one-time reminder or execution.
- Cron: recurring work. Each scheduled occurrence has its own completion status; retries can refer to its `occurrence_id`.
- The City must remain running for automatic triggers. Missed one-time triggers are surfaced for human handling rather than silently replayed.
- A due date does not start execution. Schedule pausing does not complete work.

## Actions

- `capture`: record the user's original task text immediately and prepare it in the background. Do not invent authorization or rewrite a record request as an execution request. The response includes task_id and submission_id; reuse submission_id for a retry. Saved does not mean running. Session delivery routing is captured automatically.
- `prepare`: supplement an existing task with the user's clarification or retry preparation. Use its task_id; do not create another task. Previous automatic arrangements pause until the new version is ready.
- `list`: current Agent's execution tasks and personal tasks; returns stable IDs.
- `create`: create work; use `kind=self` for personal todos/reminders. Repeating a title does not deduplicate. Inspect existing work when the user's intent is to update it.
- `update`, `status`, `enable`, `disable`, `delete`: mutate an existing task by stable ID passed in `title`.
- `run`: asynchronously execute an Agent/script task. An optional `occurrence_id` retries an unfinished recurring occurrence.
- `history`, `run_detail`: read execution history and deliverables.
- `inbox`: read unorganized work and unresolved reminders, failures, missed triggers and review items. Reading never resolves them.
- `work`: organize, start, complete, cancel, reopen, pause, resume, resolve, accept, revise or skip. Supply `task_id`; handling a particular request requires its `item_id` or `occurrence_id`.

## Completion and human control

- One-time Agent execution success submits a result for human acceptance; it does not complete the work.
- Recurring Agent work automatically completes each successful, valid occurrence unless per-occurrence acceptance is enabled in the task definition.
- Do not accept your own deliverable or mark human work complete unless the user explicitly instructs you to do so.
- Opening a result only marks its notification read. Acceptance is a separate explicit action.
- `revise` returns a result to unfinished work without starting another paid execution. Record the user's feedback in the task body before explicitly rerunning.
- Failure handling and reminders are tied to the original task. Do not create new tasks for these internal events.
- Running work cannot currently be edited, cancelled or deleted from the task workspace; report the active execution accurately.

## Execution and delivery

- `run` returns `accepted`, `message` and `executionId` immediately. When accepted, continue the current conversation without polling the run directory or forwarding the result again.
- Each run stores its input snapshot, output, result, error and execution metadata. Read history through the task API when the user asks.
- Agent runs use independent task Sessions. `review=true` enables simulated multi-round review; it is not human acceptance.
- Creating from a Session captures its Agent, Workspace, session ID and origin as a fixed delivery target. Never ask the model or user to supply Session routing fields.
- Changing execution targets does not move delivery. Without a calling Session, results remain in Task history.
- The final assistant message is the deliverable body itself, written to `output.md` and optionally appended to the captured Session. Exclude task-management commentary and long logs.
- If the work explicitly requires sending to an external channel, its executing Agent calls Messenger directly; Task result delivery does not send a Messenger message.

## Task body

For Agent execution, use a standalone delivery contract with goal, background/input, execution steps, output requirements and constraints. Another executor must understand it without the creating conversation. State exact output format and scope. Do not include task creation, scheduling management or status-report instructions in the deliverable workflow.

For script execution, use a pure script with comments describing its purpose, dependencies and failure conditions. Write user deliverables to explicit project paths.
