# Inbox

Notification 是 Desktop 默认内置的 City 级统一通知事实源。一个 City 持有一个实例，Inbox、会话列表提示、导航红点和应用图标角标读取同一快照，并通过 Power 数据变更事件刷新。

Sidebar 按“需要处理”（可响应请求与未读失败）、“通知”（普通通知）、“全部”（去重后的所有 Inbox 项目）分类；主区域以列表展示标题、摘要、来源和时间。选择后宽区域在右侧显示详情，窄区域用详情替换列表并提供返回操作。进入不自动选中，清除当前更新不自动打开或读下一条。

页面使用 Downcity 无描边布局，以留白和轻底色组织列表与详情。桌面列表固定为 360px，未选中、打开、关闭事项时保持宽度与位置；标题、数量、刷新、整理菜单和滚动消息共用完整浅底面板与统一内边距。每项左侧为独立的 32px 头像列，与文本区顶部对齐。文本首行是来源名称与紧随的时间，第二行是真实标题，下方为最多两行真实正文摘要；没有摘要时省略。请求摘要只使用公开问题或描述，不展开私密输入或审批原始参数。会话交付通知使用实际结果首个非空行作为标题，无内容时使用简短类型名；详情缺少正文时省略。右上注意力圆点和右下通知菜单各有独立槽位，悬停或键盘聚焦显示菜单，触屏常驻，不影响文字或圆点位置。列表头高 36px，仅包含分类名、数量、刷新与更多菜单。未选择时右侧留白；详情正文与表单填满剩余宽度，以统一内边距对齐来源身份、标题和内容，长代码与 Markdown 保持在可用区域内。详情顶栏同为 36px，导航操作使用统一轻量按钮，表单主次操作使用共享 32px 按钮。状态复用 Rail 注意力配色：需回应为琥珀色，失败为红色，成功与信息通知为蓝色；已读移除圆点并保留业务结果，无法响应请求显示中性中断状态。Agent 来源在列表开头和详情来源名称旁显示同一头像；头像由宿主当前 Agent 目录提供，缺省使用标准 Agent 图标，没有 Agent 的 Power 更新使用业务图标。问题、审批与私密输入复用宿主表单，相同标题只显示一次，多问题保留各题提示和导航。刷新保留输入，切换或关闭前确认未提交修改；提交成功原位确认，可主动处理下一项。

待处理请求引用原 Session 的 Interaction。查看、阅读和进入会话不会结束请求；只有原主体确认响应或请求失效才离开队列。私密问题使用原 Session 专用提交入口，明文不进入通知存储。暂时不可达的来源保留最后已知请求并显示未知状态。

“通知”保存普通结果及已读历史。具体详情在有焦点且实际可见的窗口中展示时确认该条更新；有焦点且实际可见的原会话可将该目标的普通更新标为已读。可响应待处理请求加 `scope=inbox` 的未读失败事项构成统一角标；成功和信息更新只显示未读点，仅会话回复未读不计入。进入业务 Power 工作区不批量清除未读；通知已读、撤回均不改变 Task、验收或审批状态。

通知行菜单提供“标为已读”和“清除此通知”；列表顶部整理菜单的“全部通知标为已读”确认点击时全部 Inbox 普通通知的快照，不受当前分类影响并保留记录。行操作“清除此通知”和顶部菜单“清除已读通知”只移除普通通知，不删除原会话、Task、Group 历史，同一事项后续新事件可再通知。所有动作均核对通知 ID 和 `created_at`，清除已读使用点击时的 Inbox 普通更新快照，不受当前分类影响，且要求该版本当前仍为已读；在途新事项和新版本不受迟到操作影响。原问答、审批、私密输入 Interaction 不会被这些操作清除或结束。进行中的操作禁用重复提交，失败保留内容并显示错误。

Power 快照明确提供 `pending_request_count`（可响应请求）、`unread_update_count`（Inbox 全部普通未读更新）、`unread_failure_count`（其中失败）和 `badge_count = pending_request_count + unread_failure_count`。侧栏及导航提示显示“待处理 X · 未读失败 Y”；“通知”分类单独显示全部通知未读数，Desktop 直接消费最终角标值。

宿主动作：`notification.read` 与 `notification.clear_update` 接收 `{ notification_id, created_at }`；`notification.read_updates` 与 `notification.clear_read_updates` 接收 `{ updates: [{ notification_id, created_at }] }`。动作返回状态及完整 `snapshot`，Renderer 按 `revision` 拒绝迟到快照。

普通 Agent 回复只产生会话未读，不进入 Inbox。Agent 对话失败、后台 Work Main 的结果与失败进入 Inbox，Child 结果由 Main 汇总；业务 Power 按各自交付边界发布。群聊失败进入 Inbox，待处理引用成员原 Interaction。每个会话或群聊更新同一事项，每个 Task 的多次 Run 更新同一任务事项，执行历史留在来源。原事件重投保持阅读状态，新事件或摘要变化恢复未读。来源类别、目标、展示范围和成功／失败结果由独立字段表达，界面不解析标题。

Session、Group 目标使用稳定身份，与 Workspace 绑定无关。归档、删除、Agent 或 Group 移除均保留摘要与阅读状态，并明确显示来源已归档、已移除或未知。目录核对只在启动、生命周期变化和明确刷新入口执行；查询不写入、迁移或删除通知。Interaction 的准确 origin 由原主体提供，未知来源请求仍然保留，不根据分类猜测身份。Desktop 仅适配当前平台的应用图标角标能力。

Notification is Desktop's built-in City-level source of truth for Inbox, conversation indicators, navigation dots, and the application badge. All consumers use one event-driven snapshot. Pending requests retain their original Session identity and remain pending when viewed. Private answers use the original dedicated submission channel. Unreachable sources remain unknown rather than being treated as resolved.

The Sidebar offers Needs attention (respondable requests and unread failures), Notifications (ordinary notifications), and All (all Inbox items, deduplicated). The main area presents a list with titles, summaries, sources, and times. Selection opens details on the right in a wide area; in a narrow area, details replace the list and provide a Back action. Entering Inbox does not automatically select an item. Clearing the selected update does not open or mark the next item as read.

Inbox uses Downcity's borderless layout, spacing, and subtle surfaces. The desktop list stays 360px wide at the same position before selection, while an item is open, and after closing it. Its title, count, refresh, organization menu, and scrolling messages share one subtle panel with consistent padding. Each item has an independent 32px avatar column aligned with the top of its text. The first text row shows the source name followed immediately by the time, the second shows the actual title, and up to two lines summarize the real body below. Empty summaries are omitted. Request summaries use public questions or descriptions, never private input or raw approval parameters. Session delivery notifications use the first nonempty result line as their title, with a short type name when content is absent; details omit missing body content. The upper-right attention dot and lower-right menu have separate slots. Menus appear on hover or keyboard focus and remain visible on touch without moving text or covering the dot. The 36px list header contains only the category, count, refresh, and more menu. The right area stays blank until selection. Detail bodies and forms fill the remaining width with consistent padding, containing long code and Markdown. The detail toolbar is also 36px high with matching lightweight navigation buttons; form actions use shared 32px primary and secondary buttons. States share Rail attention colors: amber for requests needing a response, red for failures, and blue for success and informational notifications. Reading removes the dot while retaining the business outcome. Requests that cannot receive a response show a neutral interrupted state. Agent avatars appear at the start of list items and beside source names in details, using the host's current Agent directory and standard fallback icon. Power updates without an Agent use a business icon. Host forms display matching titles once and retain prompts and navigation for multiple questions. Refresh preserves input, switching or closing confirms unsubmitted edits, and successful submission confirms in place with an explicit next action.

Trusted hosts supply avatars with `NotificationRendererOptions.render_agent_avatar(agent_id, size)` (`list` for the 32px independent avatar column or `detail` for the 18px source row). The public Renderer retains the real `agent_id` without resolving private avatar paths. `render_interaction(item, respond, display)` receives `display.title` and `display.title_id` for shared headings and accessible names. Desktop uses the original interaction component with `presentation="inbox"`. `render_attention({ kind, outcome, presentation, label })` supplies shared host attention visuals for `dot` and `status`; Desktop reuses Rail's `attention_from_notification` and `attention_visual`. Hosts without this port receive a neutral fallback.

Ordinary updates retain read history. Notification row menus offer Mark as read and Clear this notification; the list header's organization menu offers Mark all notifications as read and Clear read notifications. Snapshot actions only apply to ordinary Inbox versions present when clicked, across all categories, matching notification IDs and content timestamps. Clearing read updates also requires the stored version to remain read. New events remain eligible to notify, and clearing never changes conversation, Task, or Group history or original question, approval, or private input Interactions. In-progress actions disable repeat submission and report errors without removing content. Power provides `pending_request_count`, `unread_update_count`, `unread_failure_count`, and final `badge_count` in one snapshot; the sidebar and navigation explain the count components, and Desktop consumes the final badge value. Host actions `notification.read` and `notification.clear_update` accept `{ notification_id, created_at }`; `notification.read_updates` and `notification.clear_read_updates` accept `{ updates: [{ notification_id, created_at }] }`. They return status and a complete `snapshot`, whose `revision` prevents stale UI rollback. Displaying a specific update's details in a focused, visible window marks that update as read; viewing its original conversation in a focused, visible window marks that target's ordinary updates as read. The badge and Inbox navigation number count respondable pending requests plus unread Inbox failure matters. Success and informational updates retain unread dots without increasing this number. Ordinary replies remain conversation unread indicators and do not enter Inbox. Background Work Main results, failures, and original requests needing a response enter Inbox. One conversation, group conversation, or Task updates one matter; execution history stays with its source. Original event redelivery preserves read state; new events or changed summaries become unread. Source kind, target, scope, and outcome are explicit fields. Reading or withdrawing a notification never completes tasks, accepts results, or approves operations. Archived or removed Sessions, Agents, and Groups retain notification summaries and read state with explicit source availability. Reconciliation runs at startup, on lifecycle facts, or on explicit refresh. Queries never write or delete notifications. Original Sessions supply accurate Interaction origins; unknown sources remain visible. The Power owns all policies and lifecycle state; Desktop supplies application icon badge integration.
