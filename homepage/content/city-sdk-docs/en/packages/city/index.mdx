---
title: "City"
description: The runtime environment that owns Agents, Workspaces, Plugins, and transports.
---

`City` is the composition root shared by the CLI, Desktop, and custom Node hosts. Applications
create Agents. City owns Workspaces, one instance per Plugin ID,
lifecycle, Storage, Embassy services, and optional HTTP/RPC transports. Sessions remain owned by an
Agent's `AgentSessions` collection.

```bash
pnpm add @downcity/city @downcity/plugins
```

```ts
import { Agent, City, Workspace } from "@downcity/city";
import { create_builtin_plugin_registrations } from "@downcity/plugins";

const workspace = new Workspace({ id: "project", path: process.cwd() });
const registrations = create_builtin_plugin_registrations();
const city = new City({
  embassy,
  workspaces: [workspace],
  plugins: registrations,
});
const agent = new Agent({ id: "lucas", model });

city.agents.add(agent);

const session = await agent.sessions.create({ workspace });
await (await session.prompt({ query: "Summarize this project" })).finished;
await city.close();
```

## Relationships and ownership

- `City` owns the Plugin catalog, unique instances, lifecycle, and Hook scopes.
- `Agent` owns identity, model, instructions, custom tools, and `AgentSessions`; it does not own Plugins.
- `Session` belongs to an Agent and receives one Workspace execution context plus a City Plugin execution view.
- `Workspace` owns project files, tools, environment, and an optional Shell. It does not own Agents, Sessions, or Plugins.

An SDK host may call `city.plugins.add(plugin)` and `city.plugins.remove(plugin_id)` dynamically.
One Plugin ID maps to one instance within a City, shared automatically by every registered Agent.

## Workspace management

`city.workspaces.add(workspace)` transfers runtime ownership to City, while `get()` and `list()`
provide stable lookup surfaces. When a Workspace is no longer needed, call
`await city.workspaces.remove(workspace_id)`. City disposes its Shell, Sandbox, and other runtime
resources before removing it from the current City, and returns `null` when it does not exist. This
only manages the runtime object; it never deletes the project directory.

## Plugin lifecycle

A Plugin instance has one City-owned lifecycle and may register host-management Actions during
`initialize`. It has two lifecycle checkpoints:

1. City calls `initialize` once when the Plugin is added.
2. City calls `dispose` once when the Plugin is removed or City closes.

Agent, Session, and Workspace entry or removal do not trigger Plugin lifecycle callbacks. Each Plugin
owns its long-lived connections, timers, schedulers, and workers according to its actual domain key,
such as an account, Profile, or task definition.

Each Action, System provider, Availability check, and Hook call receives a freshly projected `PluginContext`. It contains
restricted `city`, `agent`, `workspace`, `session`, `turn`, `config`, and `storage` handles. A Plugin
can therefore communicate through the current Session or Agent handle instead of resolving only a
`session_id`.

Hooks remain scheduled by City's execution Registry. A Session captures an immutable Hook scope at
explicit checkpoints. New Steps stop seeing a dynamically removed Plugin immediately, while an
existing Step may finish before its scope triggers final cleanup.

The CLI daemon and Desktop window own independent City lifecycles. Host coordination only controls
listener ownership; it does not mutate persisted Agent, Plugin, or Session data.
