---
title: "City"
description: The runtime environment that owns Agents, Workspaces, Powers, and transports.
---

`City` is the composition root shared by the CLI, Desktop, and custom Node hosts. Applications
create Agents. City owns Workspaces, one instance per Power ID,
lifecycle, Storage, Embassy services, and optional HTTP/RPC transports. Sessions remain owned by an
Agent's `AgentSessions` collection.

```bash
pnpm add @downcity/city @downcity/powers
```

```ts
import { Agent, City, Workspace } from "@downcity/city";
import { create_builtin_power_registrations } from "@downcity/powers";

const workspace = new Workspace({ id: "project", path: process.cwd() });
const registrations = create_builtin_power_registrations();
const city = new City({
  embassy,
  workspaces: [workspace],
  powers: registrations,
});
const agent = new Agent({ id: "lucas", model });

city.agents.add(agent);

const session = await agent.sessions.create({ workspace });
await (await session.prompt({ query: "Summarize this project" })).finished;
await city.close();
```

## Relationships and ownership

- `City` owns the Power catalog, unique instances, lifecycle, and Hook scopes.
- `Agent` owns identity, model, instructions, custom tools, and `AgentSessions`; it does not own Powers.
- `Session` belongs to an Agent and receives one Workspace execution context plus a City Power execution view.
- `Workspace` owns project files, tools, environment, and an optional Shell. It does not own Agents, Sessions, or Powers.

An SDK host may call `city.powers.add(power)` and `city.powers.remove(power_id)` dynamically.
One Power ID maps to one instance within a City, shared automatically by every registered Agent.

## Workspace management

`city.workspaces.add(workspace)` transfers runtime ownership to City, while `get()` and `list()`
provide stable lookup surfaces. When a Workspace is no longer needed, call
`await city.workspaces.remove(workspace_id)`. City disposes the Workspace before removing it from
the current City; Workspace delegates Shell Sessions and Sandbox cleanup to its Shell. The method
returns `null` when the Workspace does not exist. This
only manages the runtime object; it never deletes the project directory.

## Power lifecycle

A Power instance has one City-owned lifecycle and may register host-management Actions during
`initialize`. It has two lifecycle checkpoints:

1. City calls `initialize` once when the Power is added.
2. City calls `dispose` once when the Power is removed or City closes.

Agent, Session, and Workspace entry or removal do not trigger Power lifecycle callbacks. Each Power
owns its long-lived connections, timers, schedulers, and workers according to its actual domain key,
such as an account, Agent, or task definition.

Each Action, System provider, Availability check, and Hook call receives a freshly projected `PowerContext`. It contains
restricted `city`, `agent`, `workspace`, `session`, `turn`, `config`, and `storage` handles. A Power
can therefore communicate through the current Session or Agent handle instead of resolving only a
`session_id`.

Hooks remain scheduled by City's execution Registry. A Session captures an immutable Hook scope at
explicit checkpoints. New Steps stop seeing a dynamically removed Power immediately, while an
existing Step may finish before its scope triggers final cleanup.

The CLI daemon and Desktop window own independent City lifecycles. Host coordination only controls
listener ownership; it does not mutate persisted Agent, Power, or Session data.
