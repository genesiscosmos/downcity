title: Architecture
description: "Core architecture layers in Downcity: console, agent, execution context, session, and power runtime"
---
Current Downcity is best understood through five layers:

1. `console`
2. `agent`
3. `execution context`
4. `session`
5. `power runtime`

## Layers

### `console`

- global control plane
- process registry
- city-level configuration and inspection

### `agent`

- owns one project runtime
- holds model access, session store, power registry, and runtime host state

### `execution context`

- shared capability surface exposed during execution
- the place powers read stable runtime abilities

### `session`

- owns one execution thread and its prompt/run state
- the unit that actually runs model + tool flow

### `power runtime`

- all capability modules are modeled as powers
- some are local and action-first
- some are managed and lifecycle-owned

## Managed vs local powers

### Local powers

- usually attached directly to one SDK `Agent`
- examples: `skill`, `web`, `sound`

### Managed powers

- runtime-owned modules that start and stop with one target agent
- examples: `chat`, `task`, `memory`, `shell`, `schedule`

## Main takeaway

Do not use the old split-layer language for the current system.

The current model is:

- session executes
- powers expose capability
- managed powers own long-lived runtime modules
