# 元数据与落盘

SDK Session 保存在 City 提供的 Agent 存储作用域中；没有 City 时默认使用内存存储。应用应通过
Session API 读写，不要把这些文件当作自己的数据库。

```text
~/.downcity/agents/<agent_id>/sessions/<origin_type>/<session_id>/
├── session.db
└── attachments/
```

一个 Session 对应一个 `session.db`。核心表为：

- `session_state`：Session 身份、配置、标题、预览和 system snapshot。
- `messages`：User/Agent Message 的 envelope。
- `message_parts`：每个 Message 的独立 Part；一个 content 对应一个 Part。

读取 API 返回聚合后的 `SessionMessage`，数据库表结构不会泄漏到 UI 或模型 Provider。Message 是
canonical history，永远不会因为上下文压缩而删除或改写。

## Composer 与上下文策略

`SessionComposer` 负责生成最终送给模型的 system、messages 和 tools。Composer 内部使用一个
`SessionContextPolicy`，例如 `SequenceSummaryContextPolicy` 会在自己的
`composer_sequence_summaries` 派生表中保存累计摘要。

派生摘要、索引和检索结果不是 Message，可以删除并重建，也不会改变用户可浏览的 canonical history。
当前策略只会读取最新摘要边界之后的 Message：

```text
最新 Policy 派生摘要
+ 边界之后的 canonical Message
```

模型返回上下文超限时，Composer 调用 Policy 的 `recover_context()` 推进派生状态；不会写入 Active、Segment 或第二份消息文件。

## 中断恢复与事务

Message envelope 与 Parts 在同一个 SQLite 事务中提交，只有提交成功后才发布 Mutation。启动时
SessionStorage 会把 streaming Agent Message 和 running Action 收口为可恢复状态。附件仍放在
`attachments/`，Message Part 只保存附件引用。

旧版本 JSONL 数据不由 Desktop 或 Runtime 自动迁移。需要迁移时，在应用外执行仓库提供的一次性脚本
`scripts/migrate-session-storage-to-sqlite.mjs`。
