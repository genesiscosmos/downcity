---
title: Power HTTP Injection
description: Understand what power.http.server does, how auth policies work, and when runtime HTTP injection is the right tool
---
A power can declare:

```ts
http: {
  runtime: {
    auth_policies: [...],
    register({ app, get_context, power_name }) {
      // register routes
    },
  },
}
```

## What problem this solves

It lets a power declare:

- which runtime HTTP routes it owns
- which auth policies those routes require

and leaves server assembly to the runtime layer.

## `auth_policies`

This describes:

- how the power-owned route group should be protected

The key idea is:

- the power declares its own security needs
- runtime and console consume that declaration

## `register`

This is where the power adds its routes to the runtime Hono app.

The power does not need to start a server. It only contributes route registration.

## When power HTTP is a good fit

Use it when:

- you want a dedicated runtime HTTP endpoint
- the endpoint belongs to one power capability surface
- you want auth, availability, and control-plane identity to stay aligned with that power

## When it is not the right fit

If you only need:

- normal session execution
- standard SDK session routes

then the built-in session HTTP layer should remain your first choice instead of building a parallel power HTTP interface.
