# Messages and Parts

`session.messages()` reads stable SQLite snapshots, paginated on Message boundaries. Use `subscribe()` for live changes.

```ts
const page = await session.messages({ limit: 50 });
for (const message of page.items) render_message(message);
```

```ts
interface SessionMessagePage {
  items: SessionMessage[];
  total: number;
  start_sequence?: number;
  end_sequence?: number;
  next_before_sequence?: number;
  has_more: boolean;
}
```

`total` is the number of real Messages in the Session, not `items.length`. `limit` defaults to 50 and is capped at 200.

## Two top-level Message types

```ts
type SessionMessage = SessionUserMessage | SessionAgentMessage;
```

| `role` | Meaning | Top-level state |
| --- | --- | --- |
| `user` | User input or an internal recovery instruction | No state field; complete when written |
| `agent` | Agent output and runtime records | `state: "streaming" \| "done"` |

A User Message does not distinguish prompt from steer. Whether it starts a Turn or joins the current Turn is represented by `turn_id` and decided by SessionLoop, not duplicated in message content.

An Agent Message's `state` only answers whether Parts can still be appended. Success, stop, and failure belong to the Turn result. Persisted stop and failure reasons use an `error` Part.

A Session has one two-party Message sequence ordered by `sequence`. Tools, Interactions, Actions, and Errors are Agent Parts rather than independent Messages. Multiple model Steps in an ordinary Tool Loop may append to the same Agent Message; model-produced Parts carry their source `step_id`.

## User Parts

| `type` | Key fields | Meaning |
| --- | --- | --- |
| `text` | `text` | User body |
| `context` | `tag`, `context` | Semantically tagged model context |
| `file` | `url`, `media_type`, `filename` | A user-submitted file |
| `data` | `data_type`, `data`, `data_id` | Persisted host/UI data not sent to the model |

User Parts have no streaming state. A `context` Part becomes safely tagged text only at the model boundary:

```ts
// Canonical User Part
{ part_id: "user-context:1", sequence: 1, type: "context", tag: "reference", context: "Earlier message" }

// Model Content
{ type: "text", text: "<reference>Earlier message</reference>" }
```

`visibility: "internal"` uses the same User Message shape. Recovery instructions that affect the next Step are persisted first and then read from canonical history by the Composer; there is no separate runtime-input protocol.

## Agent Parts

| `type` | Key fields | Meaning |
| --- | --- | --- |
| `text` | `text`, `state` | Visible output, `streaming -> done` |
| `reasoning` | `text`, `state` | Reasoning output |
| `tool` | `tool_call_id`, `tool_name`, `state`, `input`, `output` | Complete Tool lifecycle |
| `interaction` | `interaction_id`, `status`, `request`, `response` | Async approval or questions |
| `file` | `url`, `media_type`, `filename` | Agent file result |
| `data` | `data_type`, `data`, `data_id` | Structured UI data |
| `action` | `action_id`, `action_type`, `state`, `title` | Session operation state |
| `error` | `scope`, `code`, `message`, `recoverable` | Session or Turn error |

Every Part has a stable `part_id` and immutable `sequence`. A Tool state transition updates the same Part instead of creating duplicate request/result messages. A Tool and its related Interaction transition commit in one checkpoint transaction.

## Streaming and persistence boundary

```text
Events drive live rendering
Memory assembles the stream
The database stores stable semantic checkpoints
```

Model stream start, delta, and finish events first update the current Agent Message's in-memory projection and publish `part` / `delta` Mutations. Ordinary chunks do not write SQLite. When a model Step completes, the SDK validates Part identity and commits the complete Step snapshot in one transaction.

Tool transitions, Interaction changes, Actions/Errors, and Message closure are durable semantic checkpoints and may commit independently. A committed `message` Mutation replaces the live projection with a complete snapshot.

## Ordering, revision, and reconnects

Every Message has a stable `message_id`, immutable `sequence`, and increasing `revision`. Clients should:

1. Subscribe and buffer Mutations before loading the initial snapshot.
2. Merge complete `message` snapshots by `message_id + revision`.
3. Apply `part` and `delta` only while the live stream is continuous.
4. Reload snapshots after disconnect instead of assuming Deltas can be replayed.

An interrupted, unfinished Step projection may be discarded. The Session closes the persisted streaming Agent Message as `done` and appends an Error Part, so SQLite is authoritative after reconnect.

## Loading older history

```ts
let page = await session.messages({ limit: 50 });
while (page.has_more && page.next_before_sequence !== undefined) {
  page = await session.messages({
    before_sequence: page.next_before_sequence,
    limit: 50,
  });
  prepend_messages(page.items);
}
```

By default, only `visibility: "visible"` Messages are returned. Pass `include_internal: true` for debugging or audit. Composer Policy summaries are derived data: they consume no Message sequence and never appear in `messages()`.

See [Reconnect and sync](/en/agent-sdk-docs/sessions/reconnect-and-sync) for synchronization and [Metadata and storage](/en/agent-sdk-docs/sessions/metadata-and-storage) for persistence details.
