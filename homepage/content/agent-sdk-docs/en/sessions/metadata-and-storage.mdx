# Metadata and storage

A persisted Session belongs to the Agent storage scope provided by City. Without City, the default is
in-memory storage. Use the Session API instead of treating these files as an application database.

```text
~/.downcity/agents/<agent_id>/sessions/<origin_type>/<session_id>/
├── session.db
└── attachments/
```

Each Session has one `session.db` with three stable tables:

- `session_state`: identity, configuration, title, preview, and the system snapshot.
- `messages`: the User/Agent Message envelope.
- `message_parts`: one row per Part; each content value belongs to one Part.

The API reconstructs `SessionMessage` aggregates when reading. The table layout is not exposed to the UI
or model providers. Canonical history is never deleted or rewritten by context compaction.

## Composer and context policies

`SessionComposer` generates the final system, messages, and tools sent to the model. It uses one
`SessionContextPolicy`, such as `SequenceSummaryContextPolicy`, which stores cumulative summaries in
its own `composer_sequence_summaries` derived table.

Summaries, indexes, and retrieval results are rebuildable derived data, not Messages. A policy resolves:

```text
latest policy-derived summary
+ canonical Messages after the summary boundary
```

When a provider reports a context limit, Composer asks the policy to advance its derived state through
`recover_context()`. There is no public `session.compact()`, Active file, Segment file, or second
message log.

## Recovery and transactions

The Message envelope and its Parts commit in one SQLite transaction; Mutations publish only after commit.
On startup, SessionStorage closes streaming Agent Messages and running Actions left by an interrupted process.
Attachments remain under `attachments/`, while Parts store attachment references.

Legacy JSONL data is not migrated by Desktop or Runtime. Run the external one-time
`scripts/migrate-session-storage-to-sqlite.mjs` script when migration is needed.
