---
title: Agent Session
description: The agent itself is a session; get it with agent.session() and it follows the same rules as every other session
---
`agent.session()` returns the session that belongs to the agent itself. **It is the agent**: one per agent, with a `session_id` equal to the agent's `id` and a role of `origin.type = "agent"`.

The important part is that it has no special rules. It is an ordinary session, sharing the same mechanism and capabilities as every other session — workspace, `set` / `get`, messages, approvals, subscriptions.

## Get it and talk

```ts
const agent = new Agent({
  id: "coder",
  model,
  workspace,
});

const session = await agent.session();
const turn = await session.prompt({ query: "What does SessionMessages do?" });
const result = await turn.finished;
console.log(result.text);
```

The first call creates it; every later call returns the same one. A different channel, a new process, or the next day all reach the same session and the same history:

```ts
// A new process, a Telegram channel, or the next day
const session = await agent.session();
const page = await session.messages();
```

If it is archived or deleted, the next call creates a new one.

## Session roles

There is only one concept; roles are distinguished by `origin.type`:

| Role | `origin.type` | `session_id` | Purpose |
| --- | --- | --- | --- |
| The agent's own session | `agent` | the agent's `id` | The user's ongoing conversation with the agent |
| Work session | `work` | generated | Work the agent started elsewhere |
| Task session | `task` | generated | Triggered by a scheduled task |
| Group session | `group` | generated | Member sessions inside a group |

`work` is the default role. `agent.sessions.list()` reads the `work` partition by default, so the agent's own session never mixes into business lists:

```ts
const work_sessions = await agent.sessions.list();
const own = await agent.sessions.get(agent.id, "agent");
```

## Workspace capability

Like every session, the agent session carries workspace capability. The directory is an execution resource the host injects, not session identity:

```ts
const session = await agent.session({ workspace: repo_a });   // inject at creation
session.get("workspace");                                      // current instance
session.get("workspace_id");                                   // persisted identifier

await session.set({ workspace: repo_b });   // switch directory
await session.set({ workspace: null });     // leave the project context
```

`set` and `get` are the only configuration handle on a session, shared by `model` and `workspace`. Only `workspace_id` is persisted; the instance stays with the host and never enters the session.

A restored session does not get its directory back automatically — only whoever holds the workspaces knows which ones are available now:

```ts
// Without injection: no project context, but history and workspace_id still read
const without = await agent.sessions.get(session.id, "agent");
without.get("workspace");      // undefined
without.get("workspace_id");   // "repo-a"

// With injection: the host hands the instance to the session
const with_workspace = await agent.sessions.get(session.id, "agent", { workspace: repo_a });
with_workspace.get("workspace");   // repo_a
```

A failed lookup is not an error. A historical session pointing at a directory this host does not provide is normal: it then has no file tools and no shell, while plain model conversation still works.

## The agent starts its own work

The agent session receives a group of tools that other sessions do not, so work cannot spawn more work.

| Tool | Purpose |
| --- | --- |
| `session_start` | Start a work session with a task and return immediately |
| `session_check` | List every session and its state, or read one with `session_id` |
| `session_reply` | Answer a pending user interaction on another session |
| `session_stop` | Stop the turn running on another session |

Once work is started the agent session is free again and the user can keep talking; the new session inherits the current directory. To report progress the agent calls `session_check` itself, so no per-turn list injection is needed:

```text
User: Three tests are failing on CI, fix them
Agent: I'll take a look and report back
User: Also switch the README install steps from npm to pnpm
```

```text
User: How is that test fix going?
Agent: (calls session_check) Still running, 4 files changed so far
```

When a session needs user confirmation, the user still answers in the same conversation and the agent routes the answer back with `session_reply`.
