# Plugin Development Guide

A Plugin is an independent capability unit with its own actions, state, and lifecycle. The Plugin class belongs to the Agent SDK; an installable package is only an adapter for CLI/Desktop hosts.

## Design principles

- The Plugin constructor belongs to the author and is not required to accept a Profile.
- The Plugin creates and owns providers, clients, stores, queues, and long-lived resources.
- Workspace capabilities come from runtime `PluginContext`; external services use narrow injected interfaces.
- Configuration contains serializable values only. Connections, instances, callbacks, and host objects are runtime state.
- Keep one clear domain per Plugin instead of expanding it through many composition switches.

## Plugin class

```ts
import { BasePlugin, create_action } from "@downcity/agent";
import { z } from "zod";

export class ExamplePlugin extends BasePlugin {
  readonly name = "example";
  readonly title = "Example";
  readonly description = "An example Plugin.";

  constructor(private readonly client: ExampleClient) {
    super();
  }

  readonly actions = {
    status: create_action({
      description: "Return the current Plugin status.",
      input_schema: z.object({}),
      execute: async ({ context, execution }) => ({
        success: true,
        data: {
          agent_id: context.agent_id,
          workspace_id: context.workspace_id,
          call_id: execution.call_id,
        },
      }),
    }),
  };
}
```

An SDK host creates the instance directly:

```ts
const agent = new Agent({
  id: "assistant",
  plugins: [new ExamplePlugin(new ExampleClient())],
});
```

## Actions and runtime context

Every action should have explicit input, a stable result, and cancellable execution:

```ts
run: create_action({
  input_schema: z.object({ value: z.string().min(1) }),
  execute: async ({ input, execution }) => {
    execution.abort_signal.throwIfAborted();
    const result = await client.run(input.value, {
      signal: execution.abort_signal,
    });
    return { success: true, data: result };
  },
})
```

Use `PluginContext.files` for the user Workspace and `data_files` or `data_path` for private Agent/Plugin data. Never write private databases, caches, or credentials into the user Workspace.

## Lifecycle

The Plugin must create and release its own long-lived resources:

```ts
readonly lifecycle = {
  start: async (context: PluginContext) => {
    await this.client.initialize({ agent_id: context.agent_id });
  },
  enter_workspace: async (context: PluginContext) => {
    await this.client.select_workspace(context.workspace_path);
  },
  leave_workspace: async () => {
    await this.client.clear_workspace();
  },
  stop: async () => {
    await this.client.dispose();
  },
};
```

`stop` should be idempotent and release browsers, connections, timers, queues, and every other long-lived resource.

## Installable package

To support CLI/Desktop loading, declare three optional entries under one Plugin ID:

```text
example-plugin/
├── plugin.json
├── package.json
├── README.md
├── dist/agent.js
├── dist/main.js
└── dist/renderer.js
```

```json
{
  "schema_version": 1,
  "id": "example",
  "version": "1.0.0",
  "description": "A small example Plugin.",
  "readme": "./README.md",
  "agent": "./dist/agent.js",
  "main": "./dist/main.js",
  "renderer": {
    "entry": "./dist/renderer.js",
    "sidebar": true,
    "mainview": true,
    "config": false
  }
}
```

- `agent` default-exports a factory that returns a new Plugin instance for each Agent.
- `main` default-exports a management lifecycle object and registers Plugin-level and Profile configuration actions separately.
- `renderer` default-exports a paired `sidebar + mainview` and/or an independent `config`; actual slots must match the static manifest flags and use host-injected `ui.components`.
- For history and other deeper navigation, use `SidebarTreeItem` with increasing `depth` values to keep the hierarchy inside the Plugin Sidebar.
- `readme` must point to a `.md` user document inside the Plugin root. Desktop safely renders that file in the Plugin Overview.

At least one entry is required. There is no generic `entry`, `config.schema`, or host-generated form.

## Agent factory

```ts
import type { AgentPluginModule } from "@downcity/agent";

const create_agent_plugin: AgentPluginModule<ExamplePlugin>["default"] = (context) => {
  const config = parse_example_config(context.profile);
  return new ExamplePlugin(new ExampleClient(config));
};

export default create_agent_plugin;
```

A Profile is only host-side configuration space. The SDK class does not need to know it came from TOML; the factory adapts a configuration snapshot to Plugin-owned constructor parameters.

## Main and Renderer

Plugin Sidebar/Mainview use `plugin.action()` and `plugin.invoke()`, coordinate through shared `navigation`, and do not depend on a Profile. Configuration uses `plugin.config_action()` and `config.invoke()`, with Settings binding the selected Profile. Only Plugins that declare Config have Profiles. The Plugin owns structure, defaults, validation, and Secret projection; the host owns Profile CRUD.

See [Custom Plugin](/en/docs/plugin/custom) for a complete example and security boundary.

## Testing focus

- Plugin action input, result, and cancellation.
- Complete lifecycle resource cleanup.
- Agent factory returns a new instance each time with `name` matching the Plugin ID.
- main rejects invalid configuration and never leaks credentials to Mainview.
- Renderer only uses the action gateway and host `ui`.

## Release checklist

1. `plugin.json` has the correct ID, version, `readme`, and at least one valid runtime entry.
2. `agent/main` are self-contained ESM and `renderer` is a single-file React ESM bundle that shares the host React and JSX runtimes.
3. The Agent factory creates a new instance for every call.
4. Profiles contain no connections, instances, callbacks, or host objects.
5. Long-lived resources are released and asynchronous actions respond to cancellation.
6. Private data uses `data_files`; user data uses `files`.
7. Renderer code never accesses Node, Electron, Agent, or configuration files directly, and does not ship a second design system.
