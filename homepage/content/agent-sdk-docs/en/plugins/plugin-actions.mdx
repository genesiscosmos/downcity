# Plugin Actions

Plugin actions are the most direct explicit capability surface of a plugin.

An action is mainly built from:

- `allowWhenDisabled`
- `command`
- `api`
- `execute`

## The core layer is `execute`

Minimal example:

```ts
actions: {
  status: {
    execute: async ({ context }) => {
      return {
        success: true,
        data: {
          workspace_path: context.workspace_path,
        },
      };
    },
  },
}
```

`execute` is responsible for:

- receiving structured payload
- running the business logic
- returning `success / data / error / message`

Every Action call receives a readonly `execution_context` containing:

- `agent_id`: the current Agent id
- `workspace_id`: the current Workspace id
- `call_id`: the current Action call id; for model tools this is the matching Tool Call ID
- `abort_signal`: the cancellation signal the Action must honor
- `session_id` / `turn_id`: present for Session calls
- `workspace_env` / `agent_systems`: the effective configuration snapshot for the execution checkpoint

Direct CLI, HTTP, and scheduler calls receive a runtime-generated `call_id` and cancellation signal. Pass `abort_signal` to network requests, polling, and other long-running operations.

## `command`

`command` handles CLI-side mapping.

It is a good place to define:

- help text
- commander arguments and options
- how CLI input becomes structured payload

## `api`

`api` handles HTTP-side input mapping.

It is a good place to define:

- method
- path
- how an HTTP request becomes structured payload

## `timeout_ms`

An Action may declare a cooperative timeout:

```ts
actions: {
  search: {
    timeout_ms: 30_000,
    execute: async ({ execution_context }) => {
      const response = await fetch("https://example.com", {
        signal: execution_context.abort_signal,
      });
      return { success: true, data: { status: response.status } };
    },
  },
}
```

The timeout aborts `execution_context.abort_signal`. This is cooperative: the Action must pass the signal to the underlying operation. A business failure does not change the Plugin lifecycle state.

## `allowWhenDisabled`

This is one of the easiest plugin-specific details to miss.

It means:

- this action is still allowed even if the plugin is currently disabled

Typical cases:

- `status`
- `install`
- `configure`
- `models`

In other words, the actions you often need precisely because the plugin is not yet fully usable.

Without `allowWhenDisabled: true`, normal actions on a disabled plugin are blocked.

## What context does `execute` receive

Plugin action execution is designed around the `PluginCommandContext` shape.

Practically, you can think of it as:

- a stable minimal execution context for plugin work

It includes the current Agent id, project root, logger, and resolved env. Product configuration for a Plugin is passed by the upstream host when constructing the Plugin instance; actions do not read or persist it through their context.

## A slightly fuller example

```ts
actions: {
  use: {
    allowWhenDisabled: true,
    command: {
      description: "switch the default provider",
      mapInput({ args }) {
        return {
          provider: String(args[0] || ""),
        };
      },
    },
    execute: async ({ payload }) => {
      const provider = String((payload as { provider?: unknown }).provider || "").trim();
      if (!provider) {
        return {
          success: false,
          error: "provider is required",
          message: "provider is required",
        };
      }
      return {
        success: true,
        data: { provider },
      };
    },
  },
}
```
