# Plugin Configuration

City registers Plugin modules, the host configures Profiles, and an Agent references only a Plugin
ID/Profile ID:

```text
Plugin catalog registration
→ host reads and validates Profile configuration
→ City creates one (plugin_id, profile_id) instance
→ Agent binds to plugin_id/profile
→ Session receives the current Workspace execution view
```

An SDK may register modules when constructing City:

```ts
const city = new City({
  plugins: [registration],
  workspaces: [workspace],
});

city.agents.add(agent, {
  plugins: [{
    plugin_id: registration.id,
    profile: { id: "team", config: { endpoint: "https://example.com" } },
  }],
});
```

Modules and bindings may also be added dynamically:

```ts
city.plugins.provide(registration);
await city.plugins.register(agent.id, {
  plugin_id: registration.id,
  profile,
});
```

In CLI/Desktop hosts, `config.toml` is the Profile configuration source of truth. `agent.json` stores
only references, never channels, accounts, endpoints, or tokens. A Plugin main registers Config
actions, and City injects the current Profile's `get/set` store for each call.

One `(plugin_id, profile_id)` must have one consistent configuration within a City. It maps to one
shared instance and one set of long-lived resources. Plugins without Config use the `default`
Profile. Runtime connections, callbacks, and client objects must not be stored in Profile values.

A Chat Profile additionally requires one routing owner. Reuse across Agent/Workspace scopes must set
`owner_agent_id` and `owner_workspace_id` explicitly.
