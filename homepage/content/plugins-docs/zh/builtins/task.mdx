# `task` Plugin

`task` 是任务运行时 plugin。

它主要持有：

- task 相关 actions
- task system text
- 每个 plugin 实例一套 cron trigger engine

## 主要形状

- `lifecycle`
- `actions`
- `system`

## 它主要解决什么问题

当你需要这些能力时，应该关注 `task`：

- task 定义和变更
- cron 触发的 task 执行
- task 变更后的 scheduler reload

## 用户怎么使用

Task 不声明 Config。它仍会出现在 Plugins Catalog 中展示说明，同时在一级导航条贡献独立入口。它自己的 Sidebar 使用 `Task → 执行记录` 两级树；点击 Task 打开任务详情，展开 Task 时按需读取 Run。Mainview 可以新建、编辑、启停、立即运行和删除 Task，也用于展示最终输出、状态、触发来源、耗时、结果校验与错误。Task 不按 Agent 或 Workspace 分组；Task 定义与 Run 统一保存在 TaskPlugin 的 City 生命周期存储中，`agent_id` 和 `workspace_id` 只是可重新绑定的执行目标。目标失效后 Task 仍然可见、可编辑和可删除；运行中的 Task 会拒绝删除。

Task Run 成功或失败且产物落盘后会产生未读通知；跳过执行不通知。同一 Task 聚合为最新一条未读，Desktop 在 Task 图标、Task 条目、对应 Run 和系统应用角标上同步提示，打开该 Run 后自动已读。

定义已经提交但 scheduler 增量同步失败时，宿主 action 会返回同步失败详情，Desktop 会提示“Task 已保存，但调度器同步失败”。canonical `task.md` 缺失或无法解析时，TaskPlugin 会把它作为错误项暴露并停止该 Task 的调度，不会把损坏定义伪装成不存在，也不会阻止其他 Task 恢复；Desktop 可以删除错误项。

CLI 通过统一 Plugin Action 命令调用 task：

```bash
city plugin action task list <agent_id> --input '{}' --token <token>
city plugin action task run <agent_id> --input '{"title":"daily-summary","reason":"manual check"}' --token <token>
```

如果一件事应该长期存在、可编辑、可手动重跑，使用 `task` Plugin，而不是建立另一个顶层 CLI 特例。

## SDK 装配

每个 Task 必须绑定一个执行 Workspace。通过 Agent Session 调用 `create` 时，运行时会自动捕获当前 Agent、Workspace、`session_id` 与 `origin.type` 作为固定交付目标；模型不需要也不能在 action payload 中填写 Session 路由。重新绑定 Agent 或 Workspace 只改变执行目标，City 仍把结果投递到原始 Session。仅当执行与交付仍使用同一 Agent/Workspace 时，Agent Task 才继承交付 Session 的模型，否则使用执行 Agent 的默认模型。SDK 通过 City 登记内建 Task 并绑定 Agent：

```ts
const registrations = create_builtin_plugin_registrations();
const city = new City({ plugins: registrations, workspaces: [workspace] });
city.agents.add(agent);
```

cron 默认采用当前运行机器的时区。自定义时区时，直接把 `new TaskPlugin({ timezone })` 交给
City。`time:<ISO8601-with-timezone>` 一次性任务以 ISO 字符串自身的 offset 为准。

## SDK action 用法

```ts
await city.plugins.scope({ agent_id: agent.id, workspace_id: workspace.id }).run_action({
  plugin: "task",
  action: "run",
  payload: {
    title: "daily-summary",
    reason: "manual check",
  },
});
```

action 名称是 `list`、`history`、`run_detail`、`create`、`run`、`delete`、`update`、`status`、`enable`、`disable`。`history` 按时间倒序返回一个 Task 的执行摘要；`run_detail` 使用 `history` 返回的 `timestamp` 读取最终输出和错误等详情。

## 关键语义

- cron scheduler 在 TaskPlugin initialize 时从统一 Store 恢复，并由 TaskPlugin 的 City 生命周期统一释放
- cron 时区来自 constructor `timezone`，默认本机时区
- agent task 通过 PluginContext 的 Session runtime port 读取有效模型实例
- 每次执行会创建独立的 task Session，并复用宿主 Agent 的完整 Plugin 能力
- `agent_id` 与 `workspace_id` 是 Task 的执行配置；触发时才进入对应 Agent/Workspace 上下文
- Session 内调用 `create` 会自动固化当前 `(agent_id, workspace_id, origin.type, session_id)`，完成结果追加为该 Session 的 assistant 消息
- CLI、HTTP 或宿主管理界面等无 Session 调用上下文创建的 Task 不绑定交付目标，结果保留在执行历史
- create / update / delete / status 提交后会按 `task_id` 增量更新 scheduler
- 所有定义变更按 TaskPlugin 实例串行提交；one-shot 完成只条件更新最新定义
- task 运行中锁归属于 plugin 实例，reload 时也会保持同一 task 串行执行
- 运行中的 Task 会拒绝删除
- scheduler 或 timer 释放失败不会跳过其他运行与生命周期资源的收口，最终错误会聚合返回

## 公开性说明

`TaskPlugin` 从 `@downcity/plugins` 包根导出，SDK 把实例交给 City；CLI 使用统一的
`city plugin action` 调用。
