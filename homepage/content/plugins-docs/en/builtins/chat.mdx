# `chat` Plugin

`chat` is the channel runtime plugin.

It owns:

- channel state
- the chat queue worker
- the chat queue store
- chat authorization hooks and resolves
- chat-facing actions
- chat system text

## Main shape

- `lifecycle`
- `actions`
- `hooks`
- `resolves`
- `system`

## What it is for

Use `chat` when you need:

- Telegram, Feishu, or QQ chat channel runtime
- one queue worker per shared Chat Profile instance
- chat delivery and inbound message execution
- inbound user authorization, principal observation, and role resolution

## How users use it

Chat manages queues and channels in its own Config. Open Chat in the Desktop Plugins Catalog, create or select a Profile, then let an Agent reference it:

```bash
# Configure primary under Desktop Plugins Catalog / Chat
city plugin enable chat <agent_id> --profile primary
```

Use the generic Plugin Action command when you need to invoke a Chat Action from the terminal:

```bash
city plugin action chat send <agent_id> --input '{"chat_key":"telegram:123456","text":"Done"}' --token <token>
```

## SDK Assembly

An SDK host provides Chat to City through a `CityPluginRegistration` and configures channels in a Profile:

```ts
const registrations = create_builtin_plugin_registrations();
const city = new City({ plugins: registrations, workspaces: [workspace] });
city.agents.add(agent, {
  plugins: [{
    plugin_id: "chat",
    profile: {
      id: "primary",
      config: {
        owner_agent_id: agent.id,
        owner_workspace_id: workspace.id,
        channels: [{
          type: "telegram",
          id: "telegram-main",
          name: "Main Bot",
          bot_token: process.env.TELEGRAM_BOT_TOKEN ?? "",
        }],
      },
    },
  }],
});
const entry = await city.enter_workspace(agent.id, workspace.id);
```

Profiles belong to the City control plane and do not enter Agent. Chat main actions validate Profile
content and provide a credential-safe projection. One Profile owns one connection set and queue;
cross-scope bindings must select routing explicitly through the owner fields.

## Feishu dependency

`@downcity/plugins` keeps the Feishu/Lark SDK outside its default production dependencies. Apps that do not enable Feishu can import `@downcity/plugins` without installing Feishu runtime dependencies.

If your host enables `FeishuChannel`, install the SDK in that host:

```bash
npm install @larksuiteoapi/node-sdk@^1.66.0
```

Use the isolated Chat plugin subpath:

```ts
import { ChatPlugin, FeishuChannel } from "@downcity/plugins/chat";
```

When Feishu is enabled without the SDK installed, the runtime error tells you which package to install before enabling channel `"feishu"`.

## SDK action use

In an embedded SDK scenario, call the visible chat actions by plugin name:

```ts
await entry.plugins.run_action({
  plugin: "chat",
  action: "send",
  payload: {
    chat_key: "telegram:123456",
    text: "Done",
  },
});
```

The common actions are `list`, `info`, `send`, `react`, `context`, `history`, and `delete`.

## Built-in Authorization

Chat authorization now belongs to `ChatPlugin` itself. You no longer attach a separate authorization plugin.

It participates in inbound chat execution through three chat plugin points:

- `chat.observePrincipal`: records observed users and chats
- `chat.authorizeIncoming`: decides whether the current message may enter the agent based on roles and permissions
- `chat.resolveUserRole`: enriches history / queue metadata with the current user role

Authorization actions also live under `chat`:

| Action | Purpose |
| --- | --- |
| `authorization-snapshot` | read the authorization catalog, config, observed users, and observed chats |
| `authorization-read-config` | read the current authorization config |
| `authorization-write-config` | replace the authorization config |
| `authorization-set-user-role` | set a user's role for a channel |

SDK example:

```ts
await entry.plugins.run_action({
  plugin: "chat",
  action: "authorization-set-user-role",
  payload: {
    channel: "telegram",
    userId: "12345678",
    roleId: "admin",
  },
});
```

## Important runtime semantics

- channel connections and the queue worker belong to City's shared Chat Profile instance
- Agent/Workspace routing is established and released through `bind/unbind` scope lifecycle
- inbound authorization belongs to `ChatPlugin`, while still being dispatched through generic plugin hooks / resolves
- `Agent` declares only the Chat/Profile binding and does not own chat domain state

## Public status

`ChatPlugin` is exported from `@downcity/plugins`.

SDK users assemble it through City registration/Profile configuration, never by attaching a
`ChatPlugin` instance to Agent.
