当前代码里的内建 Power 能力包括：

- `skill`
- `web`
- `sound`
- `messenger`
- `schedule`
- `task`
- `memory`
- `shell`

## 包导入路径

每个面向 SDK 的内建 Power 都有独立包子路径：

| 内建能力 | 导入路径 |
| --- | --- |
| `messenger` | `@downcity/powers/messenger` |
| `memory` | `@downcity/powers/memory` |
| `skill` | `@downcity/powers/skill` |
| `task` | `@downcity/powers/task` |
| `web` | `@downcity/powers/web` |

`image` 与 `sound` 属于 City capability，不是 `@downcity/powers` 的子路径，
通过 City 配置而不是从包子路径导入。

可以使用 `create_builtin_power_registrations()` 创建默认集合，也可以按 City 的实际需要导入并
实例化指定 Power。选择发生在 City，不发生在单个 Agent。

## 这里有两个重要分组

### 面向 SDK 用户的公开能力型 built-ins

这组通常最值得普通开发者先读：

- `skill`
- `web`
- `sound`
- `messenger`

其中 `sound` 需要通过 constructor 注入 FED 模型目录、ASR 与 TTS 能力。内建 Power 统一从各自包子路径导入并显式装配。

它们最适合理解这些 Power 形状：

- action power
- hook / resolve power
- system text power
- 一般 SDK 用户也能直接理解的 lifecycle Power

### 平台内建或基础设施型 built-ins

这组也是 built-in，但更偏平台内部集成：

- `schedule`
- `task`
- `memory`
- `shell`

这类 Power 更适合拿来理解平台组装方式，而不是默认假设所有 SDK 用户都会手工挂到本地 `Agent` 上。

## 推荐怎么读

- 如果你关心用户能力型 Power：先读 `skill`、`web`、`sound`、`messenger`
- 如果你关心平台规则层：读 `messenger` 的内置授权能力
- 如果你关心基础设施模式：读 `schedule`、`task`、`memory`、`shell`

## 职责地图

| Power | 主要职责 | 主要形状 |
| --- | --- | --- |
| `skill` | 技能发现、安装指引与内容读取 | action + system |
| `web` | 联网方法论注入与依赖准备 | action + system |
| `sound` | 从 FED 发现语音模型，统一提供 ASR、TTS 与入站自动转写 | action + pipeline + system |
| `messenger` | 渠道 runtime、队列 worker、messenger 授权与角色解析 | lifecycle + actions + hooks + resolves + system |
| `schedule` | Power Action 调度基础设施 | lifecycle-only infrastructure |
| `task` | task 调度与 cron 执行 | lifecycle + actions + system |
| `memory` | Provider 可替换的长期记忆与召回 | lifecycle + actions + system |
| `shell` | shell session runtime | lifecycle + actions |

## 一个关键区别

不要把“built-in”理解成“它们的公开性完全一样”。

这些内建 Power 其实分成三类：

- 公开能力型 Power
- 平台集成型 Power
- 基础设施型 Power

也正因为如此，Power 的概念页保留在 Agent SDK Docs，而具体 Power 手册单独放在这里。
